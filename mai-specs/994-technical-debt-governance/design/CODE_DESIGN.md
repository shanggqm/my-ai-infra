## 2. 候选进入报告的判断顺序

以下是供审查的伪代码，表达判断分支；实现载体为 Skill 指令，无新增扫描器或 JavaScript 评分函数。

```text
固定请求范围与实际基线
对范围内候选问题：
  若缺少可定位事实：
    记录具体待取证内容；不列为已确认债务
  若有真实的紧急正确性、安全或数据风险：
    单列风险与处置建议；继续区分是否存在长期成本机制
  若无法解释后续哪类修改会持续付出额外成本：
    作为一次性缺陷、偏好或已排除项处理，不标为技术债
  若有有效例外、合理领域差异、生成源或已有防护解释：
    复核成本是否仍成立；不成立则排除
  若成本机制仍成立：
    事实、推断与待核验分别写明；相同根因合并
    有可靠比较基线才归因新增/放大/历史，否则标当前快照、归因未知
    根据持续成本、频率、影响与偿还代价建议治理、观察或保持现状
输出范围内报告及缺口
停止；后续实施与规则写回需在对应授权任务内完成
```

认知与责任债的已确认判断须有团队提供的上下文、明确记录或实际交接证据；代码陌生、没有 Owner 文件或 Git 作者较多都只能提示核实。候选可带成立条件进入“待核验”，不能混入已确认数量。

## 3. 代表性发现的数据形状

这是单条报告内容的 JSON 示意，方便审查字段语义；无 JSON 存储、Schema 验证器或新 API。结构中 `evidence` 的事实、因果推断和验证状态分别表达。

```json
{
  "id": "D-001",
  "title": "统一退款政策存在两个维护源",
  "categories": ["TD-06", "TD-02"],
  "evidenceStatus": "confirmed",
  "attribution": "unknown",
  "baseline": "实际运行时填入提交及相关工作区指纹",
  "evidence": [
    {"kind": "fact", "location": "实际政策文件与有效版本", "observation": "规则要求统一14天"},
    {"kind": "fact", "location": "实际App和客服入口的文件、符号与行号", "observation": "当前两处分别实现14天和7天"},
    {"kind": "inference", "condition": "下一次继续修改同一退款政策", "consequence": "需同步两个实现与用例，遗漏可再次产生差异"}
  ],
  "counterEvidence": "已核对两个入口适用同一政策；没有渠道例外或统一生成源",
  "recurringCost": ["修改", "验证", "协调"],
  "changeFrequency": "缺少历史，未知",
  "recommendation": "近期治理",
  "reason": "核心退款规则已出现分叉；可先收敛规则维护点并保护两入口行为",
  "decision": {"status": "proposed", "owner": "待确认", "source": null},
  "verification": {"static": "两处实现和政策已核对", "runtime": "未执行"}
}
```

**Review 重点**：能否从证据判断为同一业务知识；一个根因打多个标签不会重复计数；没有历史仍可说明后续成本，但不能编造发生频率、归因或收益小时数。`confirmed` 只说明静态证据足以支持当前发现，不表示运行测试通过。

## 5. 有限偿债任务示例与反例

**示例（虚构退款系统）**：

- 范围：订单与客服的同一退款时间规则；非目标：重写全部订单架构。
- 前置：已确认两个入口均使用 14 天政策，并明确边界时刻/时区语义。
- 最小动作：复用现有领域规则维护点，两个入口调用同一规则；不为两个调用新建通用规则引擎。
- 保留行为：现有身份/租户校验、错误码及资金副作用保持约定。
- 验证：两个入口分别覆盖 14 天边界、超期拒绝与越权拒绝；测试期望取自政策，不能调用被测实现造期望。
- 退出：两个入口只有一处政策维护源，业务反例和集成用例有当前通过证据；文件移动或行数下降不能作为唯一完成标准。
- 回滚：保持既有发布恢复方式；不以恢复已确认错误的 7 天政策作为安全回滚。
- 决定：建议实施，负责人待确认；没有用户授权时保持报告状态。

**边界反例**：

| 输入 | 应有结论 | 应避免的行为 |
|---|---|---|
| App 与企业客服依有效合同分别有14天和30天政策 | 合理领域差异，可能共享基础计算但无合并义务 | 仅凭代码相似强行统一政策 |
| 生成客户端里大量重复枚举，均来自同一 Schema | 核对生成源、版本与消费者，生成重复本身无多源债务 | 手工合并生成文件 |
| 仅没找到负责人文件 | 责任信息待核验，询问/查有效交接资料 | 声称团队无人掌握系统 |
| 核心模块已有严重越权，同时用户请求只分析 | 单列具体风险、建议及时处置；保留不擅自改代码边界 | 延后到普通重构队列或擅自部署修复 |
| 旧文档标记“历史方案”，当前规则有明确新入口 | 历史材料保留，不列为当前上下文漂移 | 批量改写历史 PRD/设计 |

## 6. 既有阶段的代表性增补

以下为拟加入现有流程的短约束示意，实施时合并已有相同含义的要求，避免双重清单。

```markdown
设计：对本次新增的规则维护点、契约语义、跨模块依赖和临时例外，说明当前必要性、持续修改成本及更简单备选；临时方案记录退出条件和决定依据。关键取舍在供评审代码设计中可见。

代码评审：沿真实基线区分新增、显著放大、历史存量和归因未知；用文件证据与具体后续修改说明持续成本。历史存量只有影响当前交付时才进入阻断判断，其他问题可建议独立分析。

验收：偿债需要保持现行业务不变量，并有证据说明持续成本机制得到改善；记录实际执行和未验证项。代码减少、文件重排或测试全绿不能单独证明已偿债。
```

**待用户关注**：分类与报告是否足够支撑判断；每项任务是否范围有限且可验证；阶段约束能否保持简洁；分析报告和后续执行授权是否清楚。
