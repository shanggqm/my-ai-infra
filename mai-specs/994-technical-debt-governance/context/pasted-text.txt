**在多人协作、快速迭代的 AI Coding 项目中，最值得警惕的技术债，不是“代码写得不漂亮”，而是：每增加一个需求，理解、修改、验证和协调的成本都在上升。**

这里需要区分：一个 Bug 被及时修复，未必形成显著技术债；但一种错误设计被保留下来，让后续开发不断绕路、重复排查或依赖人工兜底，就形成了持续付息的债务。这也是软件工程中技术债概念最有用的部分——关注未来修改成本，而不只是当前代码质量。[martinfowler.com](https://martinfowler.com/bliki/TechnicalDebt.html)

下面按**长期系统影响**降序整理出 **12 类典型技术债**。排序是我结合公开研究与工程案例作出的判断，主要考虑四个因素：影响范围、被后续需求反复触及的频率、跨团队偿还成本，以及是否会继续催生其他债务。

**这不是事故处置优先级。** 已经发生的越权、数据损坏或生产故障，应立即处理，不能因为对应类别排名靠后而延后。

# 一、展开版：按长期影响降序排列

## 1. 架构边界侵蚀

**问题本质：** 原本职责清晰的模块逐渐互相穿透、共享内部细节，使局部需求变成跨模块、跨团队的联动修改。

### 调研证据

Software Improvement Group 在 2026 年 5 月的分析中，用自家工具评估了 Cursor 的 FastRender 浏览器实验，发现组件紧耦合、模块化不足，架构质量评分为 2.1/5。需要强调：**这是实验性项目和厂商评分，不是企业生产系统的普遍失败率**，但它直接展示了高速生成代码可能形成的结构性问题。[SIG](https://www.softwareimprovementgroup.com/blog/architectural-debt-ai/)

### 多人迭代中如何积累

典型演化是：

> 订单需求直接修改库存表 → 退款需求直接操作账务表 → 运营后台复制这套操作 → 库存团队调整字段时，必须同时协调订单、退款和运营团队。

每个 PR 看起来都只是“少绕一层、赶紧完成需求”，组合起来却改变了系统的实际架构。

AI 还可能继续模仿这些已有模式。OpenAI 的一手工程复盘明确提到，Codex 会复制仓库中已经存在的次优模式，因此团队需要把约束固化，并持续清理偏离。[OpenAI](https://openai.com/index/harness-engineering/)

### 为什么排第一

我的判断是：**它改变的是整个系统的修改成本结构，而不是某个函数的维护成本。** 单个团队即使认真重构，也可能无法独立偿还。

最值得检查的信号是：一个本应局部完成的需求，是否越来越频繁地要求多个团队同步修改、同步测试、同步发布。

---

## 2. 数据模型与接口契约漂移

**问题本质：** 不同模块逐渐对同一实体、字段、状态或事件形成不同解释，同时缺少可靠的迁移和兼容机制。

### 调研依据

Pramod Sadalage 与 Martin Fowler 的《Evolutionary Database Design》系统讨论了多人迭代中的数据库演进：数据变更必须与代码共同版本化、测试和部署，因为数据库不仅保存结构，还保存需要持续维持业务含义的历史状态。这属于成熟的软件工程机制，而不是某款 AI 模型的专属缺陷。[martinfowler.com](https://martinfowler.com/articles/evodb.html)

### 多人迭代中如何积累

典型场景包括：

- 同一个 `amount` 字段，有人按“元”理解，有人按“分”理解。
- 同一个 `completed` 状态，订单团队理解为“支付完成”，履约团队理解为“交付完成”。
- 前后端分别维护 DTO 和枚举，新增状态只更新一端。
- 数据模型改了，但旧数据迁移、事件消费者、报表和回滚路径没有同步考虑。

**Git 可以无冲突地合并这些修改，但业务语义并不因此一致。**

### 长期利息

偿还时不仅要改代码，还要识别历史数据、核对消费者、安排兼容窗口，甚至人工判断哪些记录属于哪一代语义。

我把它排在第二，是因为：**代码可以替换，但已经写入生产的数据和已经公开的契约，通常不能直接推倒重来。**

---

## 3. 回归验证失真

**问题本质：** 测试越来越多，却越来越不能证明业务正确，导致团队失去安全修改现有系统的依据。

### 调研证据

Anthropic 的 Nicholas Carlini 在 2026 年 2 月的多 Agent 编译器实验中记录：项目后期，新增功能开始频繁破坏已有功能，他因此补建 CI 并加强约束，以减少后续提交造成的回归。[Anthropic](https://www.anthropic.com/engineering/building-c-compiler)

GitHub 在 2026 年 5 月的工程文章中也明确要求审查 Agent PR 是否删除测试、跳过检查或降低覆盖率门槛，指出“让 CI 通过”可能通过弱化 CI 实现。[The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/)

### 多人迭代中如何积累

典型路径是：

> AI 写实现，再按实现补测试 → 测试只验证当前实现的行为 → 新需求改变实现，测试跟着改 → 原来的业务约束逐渐没有任何独立验证。

另一个常见模式是：各团队的测试都大量 Mock 其他模块，自己的测试全部通过，但真实集成行为没有被保护。

**Mock、快照测试、实现细节测试本身没有错；问题是把它们当成完整的业务验收。**

### 长期利息

当测试不可信，团队就不敢重构，只能继续加兼容分支和补丁。因此，验证债会阻碍其他债务的偿还。

最值得检查的信号是：**核心规则被故意改错时，现有测试究竟能不能失败？**

---

## 4. 团队认知与责任断层

**问题本质：** 代码持续交付，但团队逐渐失去对关键设计、核心流程和变更后果的共同理解，也没有明确的人负责维护这些理解。

### 调研证据

软件工程研究者 Margaret-Anne Storey 在 2026 年 2 月分享了一次教学观察：一个快速开发产品的学生团队，在第七八周开始无法安全完成简单修改；进一步检查发现，不只是代码混乱，而是没人能够解释关键设计为何成立、模块应该如何协作。**这是观察性案例，不是企业级发生率研究。**[Margaret-Anne Storey](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/)

Simon Willison 也公开描述过自己的类似体验：通过提示词完成整项功能而没有认真阅读实现后，他失去了对系统的心智模型，进而影响后续决策的信心。[Simon Willison’s Weblog](https://simonwillison.net/2026/Feb/15/cognitive-debt/)

### 多人迭代中如何积累

例如，一个跨订单、库存和结算的需求由多个 Agent 完成。提交者只确认“功能能跑”，Reviewer 只检查局部 Diff，没有人能完整说明失败补偿和状态迁移。

下一次迭代时，大家只能重新让 AI 猜测；不同人又可能得到不同解释。

### 长期利息

每次评审、排障、交接，都要重新考古。更严重的是，团队无法区分“历史上经过权衡的约束”和“模型随手生成的选择”。

**严格说，这是与技术债相互强化的认知债、组织债。** 我把它列在高位，是因为在多人项目中，没有理解和责任主体，其他债务也很难被可靠偿还。

---

## 5. 权限与安全边界碎片化

**问题本质：** 安全规则散落在各个接口、任务和脚本里，不同开发者各自实现，导致规则不一致且无法整体验证。

### 调研依据

OWASP 明确建议：每个请求都必须执行适当的权限检查，并优先使用能够统一配置的机制，而不是依赖每个方法、每个类自行添加检查；只保证“大多数请求”检查正确并不足够。[OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

GitHub 针对 Agent 工作流的工程指导还特别要求检查：令牌权限是否过大、不可信输入是否进入执行流程、模型输出是否被直接执行、Agent 是否能接触不必要的密钥。[The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/)

### 多人迭代中如何积累

比如，一个多租户系统不断增加详情页、批量导出、后台任务和管理接口：

> 详情接口使用统一租户策略 → 导出接口自己判断角色 → 后台任务直接访问数据库 → 临时脚本使用管理员凭证。

每个新入口都变成一个独立的安全实现点。

### 长期利息

后续新增权限类型、调整租户隔离或轮换凭证时，需要全仓库查找所有例外，并且很难证明已经查全。

**这里的债务不只是“漏了一个权限判断”，而是系统没有可持续维护的安全边界。**

---

## 6. 业务逻辑重复与分叉

**问题本质：** 同一业务规则被重复实现，随后在不同需求和不同负责人手中逐渐演化成互不一致的版本。

### 调研证据

2026 年的研究《More Code, Less Reuse》在 crewAI 仓库的 617 个 PR 子样本中，发现 Agent PR 的平均最大语义冗余分数高于人工 PR。

这个指标基于代码嵌入相似度，**不能直接解释成“重复代码行数多了多少”，也不能外推到所有项目**，但它提供了比“看起来代码很多”更直接的复用不足证据。[arXiv](https://arxiv.org/html/2601.21276v1)

### 多人迭代中如何积累

例如：

> 第一版在订单模块实现优惠计算 → 第二个开发者做退款时复制一份 → 第三个开发者做报表时重新实现 → 优惠规则变更，只更新了订单模块。

真正昂贵的阶段不是最初出现两份相似代码，而是后来大家无法回答：

> 这些差异是业务故意区分，还是有人漏改了？

### 长期利息

一条规则变更，要搜索、修改、测试多个实现点；每多一个分支，就多一个被遗漏的机会。

需要注意：**应当统一的是同一个业务知识，而不是所有外观相似的代码。** 不同领域中碰巧相似的逻辑，未必适合合并。

---

## 7. 临时补丁与历史分支堆积

**问题本质：** 为赶进度添加的特殊处理、兼容代码、功能开关和过渡实现，失去退出机制后长期驻留。

### 调研依据

Pete Hodgson 在功能开关的经典工程总结中强调：开关虽然容易创建，却带来条件逻辑和额外测试负担；团队需要主动清理不再需要的开关，并为临时开关安排移除任务或到期机制。**这不意味着长期存在的运维开关、权限开关都应该删除。**[martinfowler.com](https://martinfowler.com/articles/feature-toggles.html)

### 多人迭代中如何积累

典型场景是：

> 第一版为某客户增加例外 → 第二版为了兼容旧客户端保留旧逻辑 → 第三版切换新引擎时增加开关 → 第四版需求继续兼容所有历史路径。

当没人明确说明“谁还在使用旧路径、满足什么条件可以删除”，保留就成了默认选择。

### 长期利息

新需求不再只面向当前产品，而是必须兼容多代历史实现。测试范围、排障分支和理解成本一起增加。

最值得检查的信号是：**一段代码的存在理由，只剩下“先别删，可能还有地方在用”。**

---

## 8. 错误抽象与过度设计

**问题本质：** 为追求通用、复用或所谓企业级架构，把不属于同一概念的逻辑强行统一，或提前建设没有真实需求支撑的复杂结构。

### 调研依据

Sandi Metz 在《The Wrong Abstraction》中描述了一个典型的多人演化过程：开发者 A 提取公共抽象，开发者 B 遇到不完全匹配的新需求后增加参数和条件，后续开发者继续加分支，最终公共抽象变成难以理解的混合过程。[Sandi Metz](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)

2026 年的实际 AI 使用经验也提醒我们不要把“很快生成”误当成“容易维护”。Michael Parker 在 Stack Overflow 播客中分享，自己与孩子通过 AI 快速制作游戏，直到功能迭代卡住，才发现需要面对约 2,000 行的大文件重构。这个案例说明维护负担，**并不证明所有大文件都属于过度设计**。[Stack Overflow Blog](https://stackoverflow.blog/2026/01/23/ai-can-10x-developers-in-creating-tech-debt/)

### 多人迭代中如何积累

一种路径是所有需求往“大服务”里堆；另一种看起来更专业：通用引擎、插件层、工厂、策略和配置系统迅速长出来，但真实需求只有两三个。

随后，每个开发者都必须理解这套基础设施，才能完成很小的业务修改。

### 长期利息

系统表面上“复用率很高”，实际却共享了不该共享的变化原因。修改一个业务，会迫使其他业务理解或迁就新参数。

这与上一类不同：**历史分支债是旧东西退不出去；错误抽象债是新需求被迫塞进错误结构。**

---

## 9. 故障恢复与可观测性欠账

**问题本质：** 正常流程不断扩展，但失败状态、重试语义、恢复机制和诊断证据没有同步建设。

### 调研依据

AWS Builders’ Library 详细说明了重试中的关键问题：请求可能已经成功，只是响应没有到达；缺少稳定的请求标识和幂等语义时，调用方无法安全判断是否重试。[Amazon Web Services, Inc.](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

Google SRE 则强调，监控不仅要发现显式错误，还要识别“返回成功但内容错误”等失败，并提供足够信息区分问题来源。[Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)

### 多人迭代中如何积累

比如：

> 新增同步任务只考虑成功路径 → 出错后补一个重试 → 出现重复处理后再补去重 → 状态不一致时增加人工修复脚本。

与此同时，不同模块各自决定超时、重试和异常返回形式，没有统一的错误分类和关联信息。

### 长期利息

每次事故都要临时判断“到底执行到哪一步”，恢复依赖熟悉系统的人，修复脚本越来越多。

**债务在于缺乏可重复的恢复能力，而不只是缺一条日志。** 如果每次故障都必须重新发明恢复流程，就已经在持续付息。

---

## 10. 依赖与交付环境漂移

**问题本质：** 不同成员、Agent、CI 和生产环境使用不同的依赖版本、配置与构建方式，导致交付结果难以复现。

### 调研依据

Michael Parker 在前述 2026 年播客中强调：即使模型今天生成的代码正确，依赖升级、库更新和持续维护仍然存在，不会因为代码由 AI 生成而消失。[Stack Overflow Blog](https://stackoverflow.blog/2026/01/23/ai-can-10x-developers-in-creating-tech-debt/)

pip 官方文档也明确区分了不同程度的可重复安装：只记录顶层依赖还不够，传递依赖、版本锁定和必要的哈希校验也需要考虑。[Pip Documentation](https://pip.pypa.io/en/stable/topics/repeatable-installs/)

### 多人迭代中如何积累

典型路径是：

> 一个需求引入新的 HTTP 库 → 另一个需求使用不同的重试库 → Agent 为解决安装问题升级依赖 → CI 与生产分别安装，得到不同版本组合。

没有人对整套依赖及运行环境负责，修复逐渐变成“在我的环境里能跑”。

### 长期利息

故障难复现、升级难评估、发布难回滚；业务代码没有变化，行为却可能发生变化。

这里需要避免另一极端：**永久不升级不是偿债，而是把环境漂移换成版本老化债。** 目标应是可复现、可验证地升级。

---

## 11. 性能与资源预算透支

**问题本质：** 功能不断通过小数据量测试，却持续采用无界查询、重复计算和低效访问方式，未来扩容只能靠更昂贵的补救。

### 调研依据

Anthropic 的编译器实验明确区分了功能与效率：虽然能够编译多个真实项目，但生成代码的效率仍明显落后于 GCC。这是特定实验的结果，不能作为今天所有模型的性能结论，却说明了**功能成功不等于性能目标已经满足**。[Anthropic](https://www.anthropic.com/engineering/building-c-compiler)

Django 官方性能指南同样强调，应先测量，再检查数据库访问方式、关联查询和不必要的数据获取，而不是仅凭功能结果判断实现质量。[Django Project](https://docs.djangoproject.com/en/5.2/topics/db/optimization/)

### 多人迭代中如何积累

例如，订单列表新增商品详情、优惠信息、用户等级和物流状态。每个需求都只增加一次“很简单”的查询，但这些查询放在循环内，最终每页请求触发大量数据库访问。

进一步的补救可能是增加缓存，再补缓存失效逻辑，最后形成比原问题更难维护的结构。

### 长期利息

成本随数据规模或流量上升；当访问模式、接口形状和数据结构都被后续功能依赖时，优化不再只是改一条 SQL。

我把它排在较后，是针对一般业务系统的长期维护排序；对高吞吐、低延迟或高计算成本系统，它应显著前移。

---

## 12. 有效文档与 Agent 上下文失真

**问题本质：** 仍被当作当前事实使用的文档、规则和示例已经过期，导致不同开发者和 Agent 反复基于错误前提实现需求。

### 调研证据

OpenAI 在 2026 年的工程复盘中记录，单个巨大的 `AGENTS.md` 会产生过期规则、难以核查等问题，因此改用简短入口和有结构的知识库。[OpenAI](https://openai.com/index/harness-engineering/)

Fabien Sanglard 在 2026 年 8 月的实践文章中也提到，自己曾在不同会话中反复纠正相同代码问题，后来把需要复用的约束沉淀为项目规则。[Fabien Sanglard](https://fabiensanglard.net/agent.md/)

### 多人迭代中如何积累

比如，系统已经切换到统一消息发送组件，但旧规则仍要求业务侧自行重试。新成员或新 Agent 按旧规则实现功能，又重新引入重复重试。

它与认知债不同：

> **认知债是团队不知道；上下文债是系统还在向后来者提供错误答案。**

### 长期利息与边界

同一种错误会在不同分支、不同会话里反复出现，修复无法有效积累。

**并不需要强行同步所有历史 PRD、SDD 文档。** 我的建议是：历史方案标明历史属性、避免默认当作当前事实；真正需要持续维护的是有效架构约束、现行契约、操作入口和关键决策状态。

# 二、如何理解这份排序

我对上述证据的综合判断是，多人 AI Coding 最危险的累积链条通常是：

> **局部需求快速完成 → 全局约束逐渐分叉 → 团队不再充分理解 → 测试无法保护修改 → 大家只敢加补丁 → 下一轮继续沿用已有坏模式。**

因此，**偿还技术债不应按“最难看的文件”排序，而应优先处理“业务核心、频繁修改、多人共同依赖”的交汇点。** 对稳定、很少变化且接近退役的模块，保留一部分债务可能比重构更合理。[SIG](https://www.softwareimprovementgroup.com/blog/architectural-debt-ai/)

AI 也不是只能制造债务。现有 Agent 重构研究观察到了部分结构指标的改善，只是改善并不均衡，不能把重命名、文件移动或代码减少直接等同于架构质量提升。[arXiv](https://arxiv.org/html/2511.04824v1)

# 三、精简版：标题、一句话描述、典型代码示例

以下与上面的排序一致。**代码均为我构造的简化反例，不是研究中的原始代码；数据库等接口为示意。认知债、上下文债还需要结合注释中的团队背景判断，不能仅凭代码外观认定。**

## 1. 架构边界侵蚀

**一句话描述：** 模块绕过约定接口、直接依赖其他模块的内部实现，让局部修改演变成跨团队联动。

```python
# orders/service.py
# 绕过库存和账务模块的公开接口，直接操作其内部存储。
from inventory.repository import StockRow
from billing.repository import LedgerRow

def cancel_order(order):
    StockRow.increment(order.sku, order.quantity)
    LedgerRow.update(order.id, status="REVERSED")

# 库存或账务内部模型一变，订单团队也必须跟着修改。
```

## 2. 数据模型与接口契约漂移

**一句话描述：** 同一字段、状态或接口在不同迭代中改变含义，却没有同步迁移数据和更新消费者。

```python
from decimal import Decimal

# 第一版：amount 的单位是“元”。
db.save_order({"amount": Decimal("19.90")})

# 后续迭代：改用“分”，但仍写入同一列，没有迁移或单位标识。
db.save_order({"amount": 1990})

# 历史报表仍将所有 amount 按“元”汇总。
# 新旧数据已经混存，修复不再只是改一行代码。
```

## 3. 回归验证失真

**一句话描述：** 测试依赖被测实现来生成正确答案，或只检查表面成功，无法独立保护业务规则。

```python
def test_checkout_total():
    order = make_order()

    # 用生产代码生成“正确答案”。
    expected = calculate_total(order)

    # checkout 内部也调用 calculate_total。
    actual = checkout(order)["total"]
    assert actual == expected

# 作为调用一致性测试可以；若这是金额正确性的唯一测试，
# calculate_total 算错时，两边一起错，测试仍然通过。
```

## 4. 团队认知与责任断层

**一句话描述：** 关键规则持续运行，却没有人能解释其依据、适用边界和变更后果。

```python
# 团队背景：该值由某次 AI 会话引入。
# 订单与客服团队都不知道依据，也没有决策记录或负责人。
REFUND_WINDOW_DAYS = 13

def can_refund(order):
    return order.days_since_payment <= REFUND_WINDOW_DAYS

# 代码并不复杂，但下一次调整政策时没人能确认：
# 13 是业务约定、历史兼容要求，还是模型随手选择？
```

## 5. 权限与安全边界碎片化

**一句话描述：** 各入口分别实现权限规则，随着功能增加逐渐出现校验遗漏和安全策略不一致。

```python
def get_invoice(user, invoice_id):
    return db.invoices.get(
        id=invoice_id,
        tenant_id=user.tenant_id,
    )

def export_invoice(user, invoice_id):
    require_role(user, "tenant_admin")
    return db.invoices.get(id=invoice_id)  # 漏掉租户边界

# 新增入口没有复用统一访问策略，安全审查必须逐处重新确认。
```

## 6. 业务逻辑重复与分叉

**一句话描述：** 同一业务规则被复制到多个位置，后续修改只更新部分副本，逐渐形成不一致行为。

```python
# 同一退款政策已经统一调整为 14 天。

# App 团队更新了这份实现。
def refundable_in_app(order):
    return order.age_days <= 14

# 客服团队维护的副本仍然是旧规则。
def refundable_in_support(order):
    return order.age_days <= 7

# 同一订单从不同入口申请，得到不同结果。
```

## 7. 临时补丁与历史分支堆积

**一句话描述：** 临时开关、客户特例和旧版本兼容没有退出机制，让每个新需求都背负多代历史路径。

```python
def calculate_price(order):
    if flags.enabled("pricing_v3"):
        return price_v3(order)
    if order.tenant_id in LEGACY_TENANTS:
        return legacy_customer_price(order)
    if flags.enabled("pricing_v2"):
        return price_v2(order)
    return price_v1(order)

# 迁移已完成，但旧路径没有删除计划、负责人或验证证据。
# 后续每次价格调整仍要考虑全部分支。
```

## 8. 错误抽象与过度设计

**一句话描述：** 不同业务被强行塞进通用接口，后续只能不断添加参数和条件来适配差异。

```python
def save_entity(entity, *, is_order=False, is_user=False):
    if is_order:
        reserve_stock(entity)
        calculate_tax(entity)

    if is_user:
        hash_password(entity)
        initialize_profile(entity)

    db.save(entity)

# “统一保存”混合了不同业务的变化原因，
# 新实体只能继续增加开关，调用方也必须理解内部规则。
```

## 9. 故障恢复与可观测性欠账

**一句话描述：** 失败被吞掉、执行进度未记录，出问题后只能依赖人工猜测和临时脚本恢复。

```python
def sync_order(order):
    try:
        erp.push(order)
        db.mark_synced(order.id)
    except Exception:
        return {"ok": True}  # 掩盖失败，也没有留下恢复依据

# ERP 可能已成功，数据库更新却失败。
# 下次是否重推、如何避免重复、如何定位，都没有可靠机制。
```

## 10. 依赖与交付环境漂移

**一句话描述：** 构建使用浮动版本且缺少统一依赖锁定，使同一提交在不同时间或环境产生不同结果。

```dockerfile
# Dockerfile：基础镜像和应用依赖都没有锁定。
FROM python:latest

WORKDIR /app
COPY . .

RUN pip install fastapi sqlalchemy httpx
CMD ["python", "app.py"]

# 今天通过测试的依赖组合，
# 不一定等于下周重新构建时安装的组合。
```

## 11. 性能与资源预算透支

**一句话描述：** 小数据量下可用的无界查询和重复访问被不断叠加，最终形成难以局部修复的规模瓶颈。

```python
def export_orders():
    return [
        {
            "id": order.id,
            # 每个订单再发起一次关联查询。
            "items": list(order.items.values("sku", "quantity")),
        }
        for order in Order.objects.all()  # 没有分批或数量限制
    ]

# 订单增长后，查询次数、内存占用和处理时间一起增长。
```

## 12. 有效文档与 Agent 上下文失真

**一句话描述：** 仍然生效的项目规则与真实实现脱节，使后来者反复按照旧知识引入同一种问题。

```python
# AGENTS.md 仍写着：“消息发送失败，由业务代码重试。”
# 实际现状：shared_sender 已经内置统一的有界重试。

def notify(message):
    for _ in range(3):  # 新 Agent 按旧规则又加一层重试。
        try:
            return shared_sender.send(message)
        except TemporaryError:
            continue
    raise DeliveryFailed()

# 代码已经演进，指导代码生成的上下文却仍停留在旧版本。
```
