# 编写产品规格

基于 Feature 上下文与现有产品行为，生成可评审、可指导研发的 PRD。内容结构遵循项目模板，交互细则按需读取引用。

## 前置条件

- 已确定目标 Feature，`BRIEF.md` 已记录核心需求；缺项先列明，无法唯一定位时先澄清。

## 个人偏好记忆

若已安装 my-create-memory，按[个人记忆接入约定](../my-create-memory/references/sdd-integration.md)在开始时读取当前场景的已生效偏好。只有明确长期偏好、修订或有复用价值的用户纠正才条件触发抽取；默认异步委派，主任务继续，同一证据不重复派发。已作为子任务运行时仅回传证据，由主 Agent 统一委派，不递归派发。无新证据不生成记忆；收尾核对实际落盘结果。

## 工作流

### Step 1：读取上下文

- 读取项目规则、Feature 的 `BRIEF.md`、`context/_INDEX.md` 及索引关联的需求资料。
- 核对设计、文案、业务数据等输入的实际内容与覆盖范围；无法读取或解析的标记未核验。原始素材只读。

### Step 2：探索代码库

- 阅读项目 README，定位需求涉及的模块、接口、数据模型，识别现有行为、技术约束和复用机会。
- 涉及界面或用户文案时，抽样目标端最相近的页面、公共组件、设计 token、术语和文案，作为本次方案依据。

### Step 3：梳理需求

- 按用户场景明确本次范围、功能增量及业务规则，建立与验收的对应关系。
- 区分已确认需求、代码事实和假设；关键业务歧义交需求负责人确认，不因现有实现降低验收条件。

### Step 4：生成或更新 PRD

- 读取 `mai-specs/_templates/PRD.tmpl.md`，按项目 `mai-specs/FEATURE_LAYOUT.json` 登记路径产出，缺省为 `spec/PRD.md`。模板缺失时说明缺口，先交付已明确部分的草稿。
- 涉及界面或用户可见文字时，读取并遵循 [交互与文案要求](references/interaction-and-copy.md)。章节与细节按模板、引用及本次范围裁剪。
- 已有 PRD 增量维护，保留人工批注和有效约定。产物限于 PRD 及必要图表、原型，不修改实现或项目模板。

### Step 5：质量检查

- 核对范围与验收覆盖、图文与资源一致性、编号引用和链接。
- 检查 Mermaid 语法；生成原型时检查相关展示与交互。未执行的渲染或运行检查如实标明。
- 检查关键用户旅程是否已有可判定的验收场景；新链路复杂、业务预期含糊或已有测试计划受需求变更影响时，考虑补充业务测试规划。
- 发现业务测试缺口时，简短提醒建议做什么及原因；确定开展且已有授权覆盖时，默认交由独立 SubAgent 使用可用的 `my-create-test-plan`，遵循其独立委派约定，主任务继续不依赖测试结果的工作。已有安排不重复派发；无缺口不强推。

### Step 6：收尾

- 将实际产物加入 BRIEF 索引，保持当前 Phase，不自行批准或推进阶段。
- 报告产物、缺口及已有技术方案需要同步的影响项。

## 下一步

最终答复给出一个优先下一步和可直接发送的请求，带实际 Feature 编号或路径：

- 有阻塞时，先明确首要待确认问题。
- 无阻塞时，进入技术设计；`my-create-design` 可用时给出调用请求，已有设计则提示同步更新。
