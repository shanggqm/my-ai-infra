# 对照契约审查代码

从需求与设计意图建立预期行为，沿真实执行路径审查实现，以证据支持修复、验证和合并决策。按风险与变更规模调整深度，简单变更保持简洁。

## 阶段契约

先读取本作用域的[共享阶段契约](../my-create-feature/references/stage-contracts.md)，核对有效需求来源、Profile、模板、产物路径和授权。一次调用只完成本阶段，返回实际产物、证据与缺口；后续调用、修复复评和全局 Phase / ROADMAP 由 Prompt 或主编排者安排。连续授权内主编排者继续推进，独立调用保持边界。

## 前置条件

- 已确定目标项目及 Feature、PR、分支、工作区或文件范围；存在多个候选且无法唯一定位时先澄清。
- 尽量取得需求、验收标准和相关设计。缺少关键输入时标明判断边界，先完成可做的局部评审，不从实现反推需求已经满足。

## 个人偏好记忆

若已安装 my-create-memory，按[个人记忆接入约定](../my-create-memory/references/sdd-integration.md)在开始时读取当前场景的已生效偏好。只有明确长期偏好、修订或有复用价值的用户纠正才条件触发抽取；默认异步委派，主任务继续，同一证据不重复派发。已作为子任务运行时仅回传证据，由主 Agent 统一委派，不递归派发。无新证据不生成记忆；收尾核对实际落盘结果。

## 工作流

### Step 1：理解需求与实现契约

- 读取项目规则、README 和相关需求。Feature 场景读取 `BRIEF.md`、有效需求来源与 AC、设计及必要引用（无 PRD 使用登记的替代来源），已有方案评审与测试计划按需核对；独立审查使用请求、PR 描述和已有接口契约。
- 在深入实现前，独立梳理业务目标、范围内验收条件、预期行为和不变量，区分已确认需求、设计取舍与假设。检查代码是否解决正确的问题、实现是否完整。
- 需求和设计冲突时列出影响与待决问题，不因当前代码或测试预期而降低验收条件。

### Step 2：识别变更影响与风险

- 固定比较对象，记录可复查的版本与范围，不能只写分支名或依据一次空 diff 判定无变更：
  - **分支 / PR**：确认实际 base、head 提交及 merge-base，不假定 `main`；用 `git diff <merge-base> <head>` 检查累计变更，明确是否同时包含当前工作区。
  - **工作区**：记录 HEAD，分别检查 staged（`git diff --cached`）、unstaged（`git diff`）与 untracked（`git ls-files --others --exclude-standard`）；读取相关未跟踪文件，纳入新增、删除和重命名，记录相关修改的内容指纹。
  - **文件 / 目录**：遵循用户范围，追踪必要上下游；无可靠基线时明确为当前文件审查，不编造变更来源。
- 以 Diff 为入口，沿真实调用链、数据流和状态流定位上下游、既有契约及兼容性影响。未修改的调用者、配置、数据迁移和旧客户端也可能受影响。
- 根据影响范围、失败代价和发生条件选择重点路径，优先调查权限、数据一致性、关键业务流程等实际高风险区域。通用检查项仅作为线索，不机械逐项扩展范围。
- 比较基线或工作区归属有冲突时提出具体选择，继续完成不依赖该选择的检查。

### Step 3：深入审查与失败推演

- 对照契约检查行为遗漏、偏差、过度实现及输入、输出、错误语义；将范围内验收条件关联到实现，优先级只决定调查顺序。
- 沿关键路径挑战实现假设、职责边界、抽象、依赖与复杂度，判断更简单的实现能否减少具体风险。尊重现有架构和有依据的取舍，避免无收益重构或风格争论。
- 构造反例，推演边界值、异常、并发与状态竞争、重试和幂等、部分失败及恢复；按实际变更检查权限与租户、数据生命周期、迁移兼容、性能规模等边界。
- 对每个候选问题追踪触发条件、执行路径和影响机制，按可靠比较基线区分新增、显著放大、历史存量与归因未知。历史问题只有影响当前交付时才进入阻断判断，其余可建议独立分析。
- 技术债须有文件证据，并说明下一次具体变更如何持续增加理解、修改、验证或协调成本；单次缺陷或风格偏好不足以证明债务。沿用同一发现及严重性，不追加全仓清债门槛。

### Step 4：验证问题与测试有效性

- 阅读相关测试，对照需求契约与关键失败场景检查断言、负向路径、替身边界和数据隔离。测试通过只证明实际覆盖的行为；关注空断言、放宽预期及只验证实现细节的测试。
- 对重要发现尽可能执行最小相关测试或复现，记录命令、工作目录、目标版本、退出码和实际观察。临时探针放在隔离位置，不修改受审源码或测试来让评审通过。
- 区分已确认缺陷、待验证风险与非阻断建议。缺环境或证据不足时继续探索可读上下文，给出具体补验方法；静态推断、实际执行和未验证项分别记录。宿主拒绝验证时记录限制，不关闭沙箱或换工具绕过。
- 纯静态小改动可用差异检查，不为评审引入无关测试系统。已有证据足以作出判断时收敛，避免重复验证。
- 检查现有证据是否遗漏真实用户旅程、跨模块结果或变更后需要复验的业务行为；区分开发测试补测与业务验收缺口。
- 发现业务测试缺口时，回传缺口、建议动作、依据和对交付的影响；由编排者决定是否调用 `my-create-test-plan`，本 Skill 不自行派发其他阶段。已有覆盖与安排不重复。
- 编排者已安排的业务测试可与其余审查并行；会影响合并判断的必要证据未回传时保留对应条件，不提前作无条件通过结论。

### Step 5：收敛结论与行动

- 按严重程度、发生条件、业务影响、修复成本和回归风险排序，优先建议最小有效修复。输出服务于工程决策，简单变更可合并章节，不要求凑齐问题或表格。
- 报告包含以下实际有用的信息：
  1. **总体结论**：建议合并 / 有条件合并 / 修改后重新审查，并说明依据与成立条件。缺少决定性证据时明确“证据不足，暂不能给出合并建议”。
  2. **范围与证据**：目标、实际比较基线或文件范围、相关工作区修改与指纹、检查限制；说明范围内验收条件对应的实现与测试 / 静态证据，标出未覆盖及不能判断项。
  3. **关键发现**：按 P0（阻断）、P1（重要）、P2（建议）排序，给出文件与真实行号、触发条件、问题机制、影响、变更归因、证据状态、是否阻断、最小修复及复验方式。没有重要问题时明确说明。
  4. **待验证事项**：列明影响合并判断的证据缺口、测试缺口、验证动作与完成条件，区分已执行和未执行检查。
  5. **其他建议**：仅保留收益明确的非阻断改进，不与关键发现重复。
- P0 用于有充分证据的严重正确性、权限或数据风险，阻断合并；P1 是需要处理的重要问题，说明其是否阻断及理由；P2 为非阻断建议。证据不足的风险列入待验证事项，其验证可成为合并前置条件，不伪装成已确认缺陷。

### Step 6：交付与质量检查

- Feature 场景按 `mai-specs/FEATURE_LAYOUT.json` 登记的 `code-review` 路径创建或增量维护报告，缺省为 `review/code_review.md`。保留人工批注与仍有效发现，关闭已解决项时给出复核依据。
- 独立 PR / 代码审查在对话交付；用户指定报告路径时写入该路径，无需创建 Feature 工作区。路径存在实质冲突时保留现场并明确冲突。
- 只在写入实际产物时创建父目录，不预建后续目录或添加占位文件。核对引用、真实行号、报告路径及证据与结论的一致性。
- Feature 场景若已安装 `my-create-feature`，可用其 `scripts/validate-feature.mjs --feature <实际需求路径> --artifact code-review` 只读检查路径；路径检查通过不代表内容审查或交付验收通过。
- 评审期间只写评审产物，保留原始输入、源码、测试、Phase、ROADMAP 和人工批注，不自动合并或更新验收状态。

## 下一步

最终答复给出一个优先下一步和可直接发送的请求，带实际 Feature 编号、PR 或路径：

- 有缺陷先修复并复评，`my-implement-code` 可用时给出对应请求；证据不足先补关键输入或运行验证。
- Feature 无未关闭交付阻塞时，说明代码评审流程结束，汇总当前验证结果与未验证项；需要结项时按项目约定和用户授权处理，不再要求独立验收 Skill 或额外报告。
- 独立审查完成时说明结论与剩余条件即可，不强推 Feature 流程。目标 Skill 不可用时用动作说明替代调用；已授权连续阶段时由编排者继续执行，不重复索取已有授权。
