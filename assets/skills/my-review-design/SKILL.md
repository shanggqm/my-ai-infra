# 评审技术方案

默认采用 MVP 思维，判断方案能否以最少必要复杂度完成当前可用、可验收的业务闭环。主动识别过度设计与高代价错误，按变更规模和实际风险选择审查深度。

> 评审同时检查缺失与多余。满足当前需求和硬约束即可建议通过，不把假想的企业级最终形态作为门槛；MVP 仍须保证当前必要的正确性、权限和数据保护。

## 阶段契约

先读取本作用域的[共享阶段契约](../my-create-feature/references/stage-contracts.md)，核对有效需求来源、Profile、模板、产物路径和授权。一次调用只完成本阶段，返回实际产物、证据与缺口；后续调用、修复复评和全局 Phase / ROADMAP 由 Prompt 或主编排者安排。连续授权内主编排者继续推进，独立调用保持边界。

## 前置条件

- 已确定目标方案或 Feature。多个候选无法唯一定位时，先让用户选择。
- 可读取业务目标、成功标准、技术方案与关键约束。缺少会改变核心判断的信息时，先澄清或安排针对性验证；可先完成有证据支持的局部评审。
- Feature 产物路径以 `mai-specs/FEATURE_LAYOUT.json` 为准。路径约定冲突先交用户选择；缺少契约时使用下文默认路径。

## 个人偏好记忆

若已安装 my-create-memory，按[个人记忆接入约定](../my-create-memory/references/sdd-integration.md)在开始时读取当前场景的已生效偏好。只有明确长期偏好、修订或有复用价值的用户纠正才条件触发抽取；默认异步委派，主任务继续，同一证据不重复派发。已作为子任务运行时仅回传证据，由主 Agent 统一委派，不递归派发。无新证据不生成记忆；收尾核对实际落盘结果。

## 工作流

### Step 1：理解并审视问题

- 读取项目规则、README、Feature 的 `BRIEF.md`、登记的有效需求来源与 AC、`design/TECH_DESIGN.md` 及关联决策。独立方案使用用户提供的对应材料。
- 读取方案内供评审的代码片段及其链接的代码设计附录（如同目录 `CODE_DESIGN.md`），核对其与正文的对应关系。
- 核对业务目标、真实需求、成功标准、系统上下文和约束，判断问题定义是否准确、当前方案是否必要。
- 确认本次必做与不做范围，核实规模、性能、安全及合规要求的来源。区分当前硬约束、有证据的近期要求和未来设想，不自行提高目标。
- 检查真实代码、接口、数据模型与已有测试，识别现有行为和复用条件。区分当前事实与计划新增内容。
- 需求范围或业务决策存在冲突时，指出冲突并交负责人选择，不自行改写已确认需求。

### Step 2：识别关键决策与风险

- 找出决定方案成败的架构决策、核心链路、重要依赖和隐含假设。
- 优先检查影响大、不确定性高、修复或切换成本高的事项，说明本次重点与未覆盖范围。
- 建立必要的“需求与验收 → 设计与任务 → 验证”对应关系。简单方案使用短列表，不要求补齐无关章节。
- 标出新增的数据字段、表、状态、抽象层、服务、依赖与治理能力，检查它们服务的当前需求或风险。重点识别推测性扩展、重复防护和提前建设。

### Step 3：挑战假设并推演失败

- 检验关键假设的成立条件。比较备选方案的复杂度、成本、决策可逆性和长期架构债，优先考虑满足约束的简单方案。
- 做减法推演：删除或延后某项设计后，当前验收与硬约束是否仍能满足？能满足时，提出具体删减方案及收益；不能满足时，说明必须保留的依据。
- 审视数据结构、通用化、安全、审计和可靠性建设是否超出实际场景。建议新增能力时，同样说明当前触发条件、现有能力为何不足，以及最小补救措施。
- 沿核心链路对照有效约束与真实复用点，检查职责与信任边界、数据与状态、接口契约及依赖；对跨界访问、规则副本或语义变化，指出具体后续修改成本及最小修正。临时方案须有适用范围、退出条件和决定依据。
- 核对供评审的代码设计能否帮助开发者理解核心架构、实体 / 类型、领域骨架与关键执行逻辑，并判断职责、依赖、不变量及失败处理的质量。涉及这些变更时，只有文字概述或用 TODO 隐藏关键规则须指出具体理解与判断缺口；按影响分级。simple 同样适用，低风险且无相关变化时不强求代码。片段属于设计示意，不要求完整实现，也不把它当作运行或验收证据。
- 按实际风险推演故障、异常、重试、并发和边界条件；规模增长仅在当前容量或有证据的近期需求涉及它时深入。描述具体触发条件、传播路径与后果。
- 检查实施顺序、验证手段、迁移、上线、回滚、可观测性及维护成本。仅审查本次涉及的维度。
- 历史代码问题只有影响本方案时才纳入结论；计划新增文件尚不存在不构成缺陷。

> 审查深度由风险决定。低风险文案或局部展示变更可简短完成，不机械套用清单或追加无关建设。

### Step 4：核验证据与判断

- 重要发现引用方案章节、代码路径或运行证据；能核实时附行号、版本或提交。
- 区分已证实问题、潜在风险和待验证假设。推断说明依据与成立条件，未知内容标明未核验。
- 缺失信息足以改变关键结论时，获取上下文、提出具体问题或建议最小验证；等待必要结果后再收敛结论。
- 检查反例和现有防护，剔除缺乏实际影响的建议。文档齐全、任务勾选和经验判断不能替代证据。
- 不以“最佳实践”“以后可能需要”或缺少可选章节直接判定缺陷。复杂度问题需指出具体交付或维护成本、可行的简化方式及其适用条件。
- 检查关键业务链路能否被实际验证、现有用例是否足够；有实际缺口时考虑业务测试规划，不把缺少独立测试计划直接判为问题。
- 发现业务测试缺口时，回传缺口、建议动作、依据和对交付的影响；由编排者决定是否调用 `my-create-test-plan`，本 Skill 不自行派发其他阶段。已有覆盖与安排不重复。

### Step 5：收敛结论与行动

- 综合影响、发生可能性及修复成本排序：**P0（阻断）** 为必须解决的高代价风险；**P1（重要）** 明确修正要求或接受条件；**P2（建议）** 为可延后的收益明确的改进。
- 给出 **通过 / 有条件通过 / 需要修改**。有条件通过须写明条件、验证方式与待决负责人；仍有 P0 时建议修改。关键证据不足时标记结论待定，不作无条件通过。
- Feature 报告写入登记路径，默认 `review/design_review.md`。独立方案按用户指定位置输出，未指定时在答复中给出评审。
- 报告先给总体结论与依据，再列关键发现、待验证事项和必要改进建议。每项发现说明优先级、证据、触发条件、影响及可执行动作。
- 明确区分本次必须补齐、可以删除或延后、保持现状的事项，仅列实际存在的内容。后续建设可记录触发条件，不自动加入本次任务；删减已确认需求或改变硬约束须交用户选择。
- 按规模裁剪报告；没有重要问题时明确建议通过，不凑数量。风险接受和关键业务取舍由负责人决定。
- 保留有效历史发现与人工批注，已解决项记录复核依据。核对报告路径与引用，只在写产物时创建目录。

> 评审建议不等于审批，也不替代代码评审或交付验收。只写评审产物，保持 PRD、技术方案、实现、Phase 与 ROADMAP 原状；用户另有修改授权时按授权执行。

## 下一步

最终答复给出一个优先下一步和可直接发送的请求，带实际 Feature 编号或方案路径：

- 有阻断或证据缺口时，先解决首要问题，再复评；关键选择交用户决定。
- 通过后进入实施；发现需补齐的业务测试场景时，回传给编排者安排，保留确实影响实施的前置条件。已有适用计划时不重复规划。
- 有条件通过时先落实约定条件；用户已授权连续阶段时由编排者继续执行，只提示剩余动作。
