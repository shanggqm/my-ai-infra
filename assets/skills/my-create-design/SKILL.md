# 技术方案

把已明确的产品行为转成可实施、可验证的设计与文件级任务。默认采用 MVP 思维：以最少必要复杂度完成当前可用、可验收的业务闭环，优先复用项目已有能力。

> 新增复杂度需要当前需求或风险证据支撑。未来可能需要的能力先留在范围之外；当前必要的正确性、权限、数据保护和项目硬约束仍须满足。

## 阶段契约

先读取本作用域的[共享阶段契约](../my-create-feature/references/stage-contracts.md)，核对有效需求来源、Profile、模板、产物路径和授权。一次调用只完成本阶段，返回实际产物、证据与缺口；后续调用、修复复评和全局 Phase / ROADMAP 由 Prompt 或主编排者安排。连续授权内主编排者继续推进，独立调用保持边界。

## 前置条件

- 已确定目标 Feature，可读取有效需求来源；有 PRD 则使用 PRD，无 PRD 时 BRIEF / 材料 / 会话须已明确目标、范围、行为、可判定 AC 和约束。缺项回传，不自动补建 PRD。

## 个人偏好记忆

若已安装 my-create-memory，按[个人记忆接入约定](../my-create-memory/references/sdd-integration.md)在开始时读取当前场景的已生效偏好。只有明确长期偏好、修订或有复用价值的用户纠正才条件触发抽取；默认异步委派，主任务继续，同一证据不重复派发。已作为子任务运行时仅回传证据，由主 Agent 统一委派，不递归派发。无新证据不生成记忆；收尾核对实际落盘结果。

## 工作流

### Step 1：读取上下文

- 读取项目规则、目标 Feature 的 `BRIEF.md`、实际有效的需求来源与 AC、相关决策和已有评审。
- 检查涉及的真实入口、调用端、模型、配置和测试。区分已存在路径与拟新增路径，记录代码基线和规格来源。
- 明确本次必须完成的用户路径、验收条件和不做范围。规模、性能、安全或合规要求以实际部署场景、已有约束和证据为准，不自行补成企业级目标。
- 关键范围、权限、成功条件或方案取舍存在实质冲突时，说明差异与选项，让用户选择；不自行修改已定需求。可先设计不受影响的部分。
- 更新已有方案时，保留人工批注、有效任务和决策，修改后复核下游影响。

### Step 2：确定产物路径

- 读取 `mai-specs/FEATURE_LAYOUT.json` 中的本阶段产物路径。后文路径为默认值，独立使用且缺少契约时沿用默认值。
- 与项目规则或既有文件存在实质冲突时，保留现场，让用户选择。
- 仅在实际写入产物时创建父目录；辅助图表与附录同样按需创建。保留已有空目录和占位文件。

> 不预建后续目录或添加 `.gitkeep`。缺少未来阶段目录正常，目录或文件存在不代表阶段完成，路径检查通过也不代表验收通过。

### Step 3：生成或更新技术方案

- 按共享契约选模板：已有方案增量维护；新文档优先显式模板，simple 用项目 `mai-specs/_templates/simple/TECH_DESIGN.tmpl.md` 或本 Skill 的[简版模板](assets/templates/TECH_DESIGN.simple.tmpl.md)，standard 用项目 `mai-specs/_templates/TECH_DESIGN.tmpl.md`。坏覆盖模板不绕过；资源缺失可交草稿并说明缺口。
- 开头记录 Profile、实际模板及需求来源。无 PRD 时在“需求依据与验收”持久化充分输入与稳定 AC；旧项目模板固定 PRD 字段可填写实际来源并说明，不制造假链接/文件。后补 PRD 时按共享契约迁移引用、保留技术内容与历史。
- 先给出满足已确认范围的最小方案，再说明关键取舍。模板按实际变更裁剪，无关章节、空表和重复说明直接省略；简单变更可用短文与任务列表完成。
- 优先复用已有模块、数据结构、接口和依赖。新增字段、表、状态、抽象层、服务或基础设施时，说明它解决的当前问题，以及更简单方案为何不足。
- 对本次规则维护点、契约语义和依赖变化，说明新增的持续理解、修改、验证或协调成本。临时方案在现有决策中记录理由、更简单备选、决定依据和退出条件，相关取舍体现于供评审代码。
- 按下述“供评审的代码设计”约束输出关键骨架与代表性代码，帮助开发者建立认知、掌控系统并判断设计质量；simple / standard 及项目覆盖模板均适用。
- 不为假想复用、增长或多租户预建扩展点，不默认加入通用框架、复杂配置、完整审计平台或高可用体系。实际需要这些能力时，设计到满足本次约束的程度。
- 安全与可靠性措施沿当前业务链路确定。复用有效防护，覆盖真实失败后果；不把低概率、低影响的设想一律升级为交付门槛。
- 对尚不确定的关键技术点，优先提出最小验证。可逆选择先用简单实现；高代价且不可逆的选择补齐证据或交用户决定。
- 收敛前做一次减法检查：移除某项设计后，若当前验收与硬约束仍能满足，就优先删除或延后。确有价值的后续能力只记录触发条件，不提前实现；已确认需求的删减交用户选择。
- 按路径契约写入技术方案，缺省为 `design/TECH_DESIGN.md`，开头按实际输出位置计算返回 BRIEF 的链接。
- 必要时拆出辅助图表或附录，主文档链接实际文件，共享契约只定义一次。
- 检查本次接口、状态或异步链路变化是否留下业务验证缺口，或使已有用例失效；仅针对缺口考虑补充或更新测试计划。
- 发现业务测试缺口时，回传缺口、建议动作、依据和对交付的影响；由编排者决定是否调用 `my-create-test-plan`，本 Skill 不自行派发其他阶段。已有覆盖与安排不重复。

#### 供评审的代码设计（for review check）

- 本次涉及核心架构、关键实体 / 类型抽象、领域模型骨架、核心或高风险模块变更时，必须提供足以评审的代码设计。覆盖实际变化的模块职责与依赖、关键类型 / 接口、状态转换与不变量，以及决定正确性的代表性逻辑；低风险文案、样式等无适用代码时简述原因即可。
- 沿用项目语言、组织方式和已有抽象，用类型 / 函数签名、局部 diff、代码骨架或明确标注的伪代码表达。说明现有与拟新增内容、变更前后语义、对应文件 / 符号及需要 Review 的问题；无相关变化的既有契约直接引用，不强加领域分层或新抽象。
- 核心规则、关键分支与实际涉及的权限、并发、幂等或失败恢复处理须展开到可判断质量的程度，不能用 TODO、省略号或空函数隐藏待审决策。外围样板可省略，但须说明省略边界、假设和待验证点。
- 输出以理解和审查设计为止，不生成完整业务实现，不向生产源码写入实现文件。标明片段是设计示意及其验证状态，不把示意代码当作已实现、可运行或测试通过的证据。
- 少量代码直接放入技术方案相关章节。代码较多、跨模块展开妨碍主文阅读时，单独写入技术方案**实际所在目录**的代码附录，默认候选名 `CODE_DESIGN.md`。先核对主文、layout 已登记产物的 basename（忽略大小写）及现有文件用途；主文或其他阶段产物不能充当附录。优先增量维护合法的同用途附录并保留批注；默认名被占用或 basename 已登记时，使用 `CODE_DESIGN-02.md` 等未占用且未登记的名称，不覆盖无关文件。不按固定行数机械拆分，不预建空附录。
- 拆分后主文保留评审重点、对应模块和附录相对链接；代码设计文件链接返回主文，并按模块组织代码与审查问题。片段只维护一份，方案变更时同步正文、附录和链接；自定义方案路径同样遵守同目录规则。

### Step 4：收尾

- 登记自身产物、需求来源、任务和缺口，保持当前 Phase；是否达到 ready 由编排者核对内容、必要门槛与项目定义后决定。
- 已有 `dev`、`review`、`done` 状态保持。用户明确重开时，按项目约定记录原因，不因编辑方案退回 `ready`。
- 报告设计路径、实施前阻塞及可进入的下一步。

> 设计文档完成不代替方案审查、用户业务决定或实现验收。

## 下一步

最终答复给出一个优先下一步和可直接发送的自然语言请求，带实际 Feature 编号或路径：

- 有阻塞时，先明确需确认的关键取舍或缺失的接入上下文；需要用户选择时，以具体问题收尾，补齐后再评审。
- 方案足以评审时，建议按实际风险与项目要求安排方案审查，核对方案与有效需求来源、真实代码。`my-review-design` 可用时，给出带实际 Feature 的调用请求。
- 目标 Skill 仅在项目配置或当前环境中可用时给出调用指令；否则描述要完成的动作，不伪造已安装入口。
- 用户已授权连续阶段时，由编排者继续执行，最终只提示仍未完成的动作，不重复索取已有授权。
- 当前流程已结束时，明确结束即可，不凑后续调用。

> 下一步建议不代表已执行、批准、状态推进或提交、发布授权。方案建议仍需相应决定，不能写成已获批准。
