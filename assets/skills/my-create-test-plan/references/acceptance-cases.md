# 业务用例规格

## 一份计划，按需展开

- 范围与依据：实际 Feature、需求来源、本次变更及待验业务范围。只记录足以定位输入的信息，不为普通计划维护整套摘要、ID 或状态体系。
- 已有覆盖：用短表或列表引用相关测试、执行入口与覆盖边界。区分“已有测试”和“有当前有效通过结果”；缺开发测试列补测项，不展开成第二套用例。
- 待验业务用例：仅细化需要人或 AI 操作和观察的部分；需求不明的场景保留问题，不编造预期。
- 待确认与执行条件：列出会影响当前用例的规则、地址、账号、数据或工具缺口；已承诺但暂时无法验证的场景仍在范围内。
- 只规划时不生成执行结果；请求验收时记录实际结果或未能启动的受阻原因。小需求直接记在计划末尾；项目已有报告则链接复用，不另建重复报告或强制 YAML / JSON 清单。

## 人与 AI 共用的用例格式

沿用已有编号；没有时只为需要展开的用例分配 TC 编号。需求沿用登记的有效来源（PRD、设计中的需求依据或已归档规格）的 ID 或章节引用，不复制一套验收标准。

```markdown
### TC-01：<业务场景>

- 关联需求：<有效需求来源的 AC ID 或章节链接>
- 前提与数据：<环境、账号角色、初始状态、必要输入；未知项写待确认>
- 操作步骤：
  1. <用户或系统调用方的操作>
  2. <下一步操作>
- 预期结果：<可观察的业务结果，必要时逐步对应；异步结果的等待条件来自契约>
- 验证方式与证据：<已有自动化 / AI 浏览器 / 人工等；需要保留的结果、截图或日志>
- 清理：<本用例需要的恢复动作；无副作用可省略>
```

前端用例关注交互、展示及业务状态；跨层用例要观察真实链路结果；后端业务用例可通过 API、事件或任务入口完成。Mock 用例注明其覆盖边界，不能替代真实链路证据。专项指标必须有需求或项目约定来源。

偿债用例引用对应发现与现行契约，验证保留行为和成本机制。例如收敛退款规则时，分别验证受影响入口的边界与拒绝场景，并核对规则只需在一个有效源修改；搬文件或复用被测函数生成预期均不能替代这些证据。

## 结果与增量更新

- 每次实际执行记录时间、被测版本（有未提交改动时说明相关差异）、环境及用例范围；逐项记录结果、实际观察和证据。命令执行保留实际命令、cwd 和退出结果，浏览器执行保留必要观察或截图。
- 使用通过、失败、未执行、受阻、待核验等直观状态。必要项失败或未验证时，不给整体通过结论；流程走完或命令退出 0 不能代替预期核对。
- 原始报告和历史执行事实保留；变更只标记受影响项需复验，未受影响且仍有效的证据可以复用。没有旧基线时如实说明，不能编造变更历史。
- 重复调用保留编号、人工批注和有效内容；不凭时间戳制造新方案，不为追踪增加无关表格。

旧项目模板固定写 PRD / PRD AC 时，在产物说明它对应本次实际有效需求来源；引用真实 AC，保留用户模板及批注，不补造 PRD 或重复 AC 真源。
