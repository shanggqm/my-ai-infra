# 编写业务测试计划

从用户或系统调用方的视角，明确如何验证本次业务结果。按需求成熟度和已有测试覆盖，生成供人或 AI 执行的用例；同一 Feature 可在需求、开发、提测和变更后重复调用。

## 阶段契约

先读取本作用域的[共享阶段契约](../my-create-feature/references/stage-contracts.md)，核对有效需求来源、Profile、模板、产物路径和授权。一次调用只完成本阶段，返回实际产物、证据与缺口；后续调用、修复复评和全局 Phase / ROADMAP 由 编排 Skill 或主编排者安排。连续授权内主编排者继续推进，独立调用保持边界。

## 前置条件

- 已确定目标 Feature，能够读取业务目标、范围与预期行为；无法唯一定位时先澄清。
- 早期规划无需完整技术设计、源码或测试环境。缺失信息列为待确认，先完成可确定部分。
- 主 Agent 确定开展本 Skill 时，默认按 [独立委派约定](references/delegation.md) 交给 SubAgent；用户指定主 Agent 执行或宿主不支持时按约定降级。已经作为该测试子任务运行的 Agent 直接执行以下流程，不递归委派。

## 个人偏好记忆

若已安装 my-create-memory，按[个人记忆接入约定](../my-create-memory/references/sdd-integration.md)在开始时读取当前场景的已生效偏好。只有明确长期偏好、修订或有复用价值的用户纠正才条件触发抽取；默认异步委派，主任务继续，同一证据不重复派发。已作为子任务运行时仅回传证据，由主 Agent 统一委派，不递归派发。无新证据不生成记忆；收尾核对实际落盘结果。

## 工作流

### Step 1：读取上下文

- 读取项目规则、Feature 的 `BRIEF.md`、登记的有效需求来源与 AC、已有测试计划与相关设计（PRD 可省略）；按需查看受影响代码、测试及执行结果。
- 预期结果以需求和已确认业务规则为依据，不调用被测实现计算期望。实现行为用于识别差异，不因实现现状降低验收条件。

### Step 2：确定本次工作

- 需求与设计阶段：提炼关键业务场景及可观察预期，指出歧义；暂不猜操作细节、接口字段或性能阈值。
- 开发中或提测前：结合已有测试覆盖，将待验业务场景细化为人或 AI 可执行的用例。不同成熟度的切片分别处理。
- 需求或实现变化后：只更新受影响的用例与回归范围，保留有效内容、用例编号和人工批注；相同输入不重复建例。
- 用户明确要求执行或验收时：复用现有工具验证这些场景并记录结果。只请求测试方案时不自动启动测试、浏览器或服务。
- 用一句话说明本次做什么及理由；依据实际信息判断，不以 Phase 或文档存在推定就绪。

### Step 3：复用已有测试，找出业务缺口

- 构建、静态检查、单元、组件、常规接口及必要集成测试由实施流程负责。本 Skill 引用相关测试入口、覆盖范围及可用结果，不把代码断言重复翻译成自然语言用例。
- 核对已有测试是否覆盖当前需求和版本；测试存在、旧报告通过或只有 Mock 的局部验证，均不能证明当前真实业务链路已通过。开发测试缺失时列具体补测项，交实施流程处理。
- 重点补充关键用户旅程、UI 展示与交互、相关异常和权限边界、跨模块结果以及受改动影响的既有流程。已有充分覆盖的场景直接引用，避免重复设计和执行。
- 纯后端也可有业务端到端场景，例如提交任务、查询进度、核对最终结果；按真实服务入口验证，无需强行增加 UI。
- 性能、压力、安全或故障恢复专项只在明确要求或本次风险需要时提出。低风险静态改动可以只有简短检查，不套全量测试清单。
- 偿债任务同时验证受影响的业务不变量与成本机制改善；保留前后证据。代码减少、文件搬移或覆盖率上升不能单独证明偿债完成。

### Step 4：生成或更新测试计划

- 读取 `mai-specs/_templates/TEST_PLAN.tmpl.md`，按 `mai-specs/FEATURE_LAYOUT.json` 的 `test-plan` 路径产出，缺省为 `test/TEST_PLAN.md`；无模板时按 [业务用例规格](references/acceptance-cases.md) 组织。
- 旧项目模板的“PRD AC”字段可引用实际登记的设计/归档需求 AC；在产物说明来源，不改模板原文或补占位 PRD。既有批注保留。
- 一份计划只保留本次范围、已有覆盖、需要补验的业务用例和待确认事项。早期可只写场景与预期；提测时再补账号、数据、步骤、证据和清理方式。省略空章节，不预建后续目录。
- 用例的最小字段和结果记录遵循 [业务用例规格](references/acceptance-cases.md)。具体操作可由执行者根据页面或契约确定，不提前绑定 DOM 选择器或内部函数。
- 保留已有用例和报告的唯一来源，按实际路径链接 BRIEF 及引用资料；路径或业务约定冲突时保留现场并说明。

### Step 5：按请求执行与核对

- 仅在用户要求执行时读取 [最小执行依赖](references/toolchain.md)，检查相关工具、应用地址、账号和测试数据。已有授权内推进，缺能力时列最小补齐项，不自动安装整套测试工具。
- 复用项目已有自动化入口或浏览器 / Computer Use 完成业务用例；不要求每次验收都生成自动化脚本。需要长期重复回归的稳定场景，可建议在实施流程沉淀脚本。
- 记录实际观察与必要证据，核对当前被测版本和环境。失败先定位原因，不删用例、放宽断言、降门禁或修改业务标准求绿；修复实现、改 CI、安装依赖等操作遵循已有任务授权。
- 未执行写未执行，缺条件写受阻，证据不足写待核验；旧结果受变更影响时标明待复验。只有本次范围的必要条件均有有效通过证据，才能给出该范围通过结论。

### Step 6：收尾

- 核对用例是否对应需求、是否重复已有覆盖、预期是否可判定，以及引用和链接是否有效。计划完成与实际验收结果分别说明。
- 报告产物、仍需补测或确认的事项；执行过则报告实际结果与未覆盖范围。保持原 Phase，不自行批准、标记完成或发布。

## 下一步

最终答复给出一个优先下一步和可直接发送的请求，带实际 Feature 编号或路径：

- 有需求歧义先确认；缺开发测试先补测；缺环境先补齐；用例就绪后执行业务验收。
- 仅对可用 Skill 给调用指令，其他情况直接描述动作。已有连续工作授权时由编排者继续执行；当前流程结束时无需追加步骤。
