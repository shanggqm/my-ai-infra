---

为当前仓库创建或更新根目录的 `AGENTS.md`，按如下步骤完成。

## 步骤 1：调研代码库

### 1.1 收集仓库事实

阅读以下文件，不存在的跳过：

- 项目说明：`README.md`、`CONTRIBUTING.md`。
- 清单与环境配置：`package.json`、`Cargo.toml`、`pyproject.toml`、`go.mod`、`pom.xml`、`build.gradle`、`.nvmrc`、`.node-version`、`.python-version`、`.tool-versions`；结合锁文件识别实际包管理器。
- 执行入口：`Makefile`、`justfile`、`scripts/`、构建配置、`Dockerfile`、Compose 配置、`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile`。
- 已有 Agent 说明：根目录和子目录的 `AGENTS.md`、`CLAUDE.md`、`.claude/rules/`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`、`.windsurfrules`、`.clinerules`。
- 规范与契约：开发和测试文档、`docs/adr/`、API Schema、数据库迁移、代码生成配置、lint 和格式化配置。

### 1.2 重点核实：

**A. 如何开发**

- 实际使用的语言、框架、运行时版本和包管理器。
- 安装、启动、构建、lint、类型检查、单元测试、集成测试等命令。
- 命令执行目录、环境要求、外部依赖和潜在副作用。

**B. 如何定位代码**

- 单项目或 monorepo 的组织方式。
- 核心模块的职责、依赖方向和代码入口。
- 唯一可编辑源、自动生成目录、历史实现与当前实现的区别。

**C. 哪些约束不能破坏**

- 业务不变量、接口兼容性、数据一致性、幂等性。
- 租户隔离、鉴权、权限边界和敏感操作要求。
- 已有架构决策、技术取舍及必要的历史原因。

优先采纳明确文档约定，或代码与测试能够共同证明的事实。约束应具体到字段、行为或模块边界，避免空泛描述。

**D. 如何验证**

- 不同变更类型对应的实际检查与测试。
- CI 门禁、完成标准及特殊测试环境。
- 哪些验证依赖容器、浏览器、数据库或外部服务。

**E. 有哪些特殊约定**

- 分支、提交、发布和数据库迁移要求。
- 禁止直接编辑的文件与目录。
- 特殊授权、兼容策略和维护流程。

### 1.3 调研边界

- 不扫描 `node_modules/`、构建产物、缓存及其他大型生成目录。
- 不读取真实凭据，不输出敏感配置值。
- 不为调研执行安装、部署、数据迁移或其他可能改变环境的操作。

## 步骤 2：核实并筛选要写的内容

### 2.1 事实核实

| 内容   | 核实要求                                                                  |
| ------ | ------------------------------------------------------------------------- |
| 命令   | 对照 scripts、Makefile 或实际脚本，确认名称、参数、目录、前置条件和副作用 |
| 路径   | 确认文件存在、职责准确、引用有效                                          |
| 约束   | 保持已有规范原意；代码与规范冲突时记录差异，不自动将实现视为新规范        |
| 架构   | 只记录有依据的模块边界和架构取舍，不推测设计原因                          |
| 作用域 | 模块专属规则不提升为全仓规则，优先保留局部说明入口                        |

如果已有 `AGENTS.md`，逐条处理：

- **保留**：仍有效的项目约定、业务边界、授权要求和验收标准。
- **更新**：已有新来源能确认的过时路径、命令和事实。
- **合并**：重复表达同一要求的条目。
- **删除**：产品宣传、通用编程常识、完整目录树、任务进度，以及已确认失效的说明。

无法确认是否失效的明确要求先保留。缺少普通信息就省略；只有冲突会导致改变业务承诺、扩大权限或降低验收标准时，才集中询问必要问题，其余内容继续完成。

## 步骤 3：编写 AGENTS.md

以 `# AGENTS.md` 开头，用一句话说明文件用途。正文主要使用中文，按以下七节组织；没有实际内容的章节、子标题和表格行直接省略，编号随之调整：

1. **项目概况**：用“项目、技术栈、架构、工程取舍”四行表格交代开发背景，每行一句话，不复制产品介绍。
2. **仓库结构**：一级目录列全，二级目录列重点。
3. **开发命令**：用“操作、命令、说明”表格列出实际入口，表格下说明工作目录、版本来源及特殊环境要求。不复制整份 scripts。
4. **规则与约束**：按“业务规则、架构边界、工程约定、安全与权限”分组，每条写一个具体要求。保留必要的原因、历史例外和已有授权边界。
5. **验证要求**：用“变更类型、必须执行的验证”表格关联实际检查命令，补充已有完成标准和 CI 门禁。仅列项目实际存在的变更类型与验证要求。
6. **知识与参考**：仅列举重要的，不经常变化的仓库级的架构、设计、测试、开发等各种规范以及可能存在的业务领域知识，SDD的需求相关文档不需要列。
7. **维护约定**：列出已有的文档同步要求、局部规则和任务材料归属、规范变更流程。不要凭空增加审批制度。

标题、表头和说明主要使用中文，命令、路径和代码标识符保留原文。已有文件如有明确语言要求，沿用该要求。使用普通 Markdown 链接，不使用 Claude 专属的 `@path` 导入语法。

不要加入“编写高质量代码”“充分理解需求”等通用提醒，也不要把本次调研步骤、固定思考轮数、自检次数或子代理编排写进 AGENTS.md。已有必要的操作顺序和验收要求保持完整，不为缩短篇幅而删除。

下面是虚构任务服务仓库的格式示例。参考它的结构和具体程度，根据当前仓库的发现替换内容、删减章节；所有命令、路径、字段和规则必须有实际依据，禁止照搬或留下占位符。

````markdown
# AGENTS.md

> 本文件记录项目特有的事实、约束和工作入口，详细知识按需查阅。

## 1. 项目概况

| 项目     | 说明                                                   |
| -------- | ------------------------------------------------------ |
| 定位     | TaskHub，面向多租户的异步任务服务                      |
| 技术栈   | TypeScript、Node.js、PostgreSQL、Redis                 |
| 架构     | pnpm monorepo；API 与 Worker 独立发布                  |
| 工程取舍 | 消息兼容性、租户隔离和任务可恢复性优先于局部实现简洁性 |

## 2. 仓库结构

```text
.
├── services/
│   ├── api/             # 鉴权与任务提交
│   └── worker/          # 异步执行、重试与恢复
├── packages/
│   ├── domain/          # 共享业务规则
│   └── client/generated/ # 从接口契约生成的客户端
├── contracts/           # API 与队列消息契约
└── docs/                # 架构、任务状态与开发说明
```

## 3. 开发命令

| 操作       | 命令                             | 说明                     |
| ---------- | -------------------------------- | ------------------------ |
| 安装依赖   | `pnpm install --frozen-lockfile` | 按锁文件安装             |
| 启动依赖   | `pnpm dev:deps`                  | 启动本地数据库与队列     |
| 本地开发   | `pnpm dev`                       | 启动 API 与 Worker       |
| 代码检查   | `pnpm check`                     | lint、类型检查与单元测试 |
| 集成测试   | `pnpm test:integration`          | 先启动本地依赖           |
| 生成客户端 | `pnpm generate:client`           | 会更新客户端生成目录     |

- 工作目录：仓库根目录。
- Node.js 版本以 `.node-version` 为准，pnpm 版本以 `package.json` 的 `packageManager` 为准。
- 测试使用模拟模型服务，无需真实模型密钥；配置见 [开发说明](docs/development.md)。

## 4. 规则与约束

### 业务规则

- 创建任务的幂等键为 `(tenant_id, request_id)`；重复请求返回原任务，不重复扣费。
- 自动重试生成新的 `attempt_id`，保留原 `task_id`。

### 架构边界

- `packages/domain/` 不依赖 Web 框架、队列 SDK 或 ORM。
- API 与 Worker 独立发布，队列消息变更必须兼容尚未升级的消费者。
- `services/worker/legacy/` 只维护旧任务，新处理器放在 `services/worker/handlers/`。

### 工程约定

- 修改客户端接口时先改 `contracts/openapi.yaml`，再生成客户端；不要手改生成文件。
- 已发布的数据库迁移保持不变，通过新增迁移修改结构。

### 安全与权限

- 租户身份取自服务端鉴权上下文，不信任请求体中的 `tenant_id`。
- 发布包和执行共享环境迁移需要当前任务的明确授权。

## 5. 验证要求

按变更范围合并对应检查，CI 门禁见 `.github/workflows/ci.yml`。

| 变更类型             | 必须执行的验证                           |
| -------------------- | ---------------------------------------- |
| 仅文档               | `pnpm docs:check`，检查格式与链接        |
| API 或 Worker 代码   | `pnpm check`                             |
| 任务状态、重试或恢复 | 另运行 `pnpm test:integration`           |
| 公共接口或队列消息   | 另运行 `pnpm test:contracts`，验证兼容性 |

**完成标准**

- 满足需求及上述项目约束。
- 报告实际执行的检查及结果，明确未验证项、阻塞原因和剩余风险。
- 未执行或失败的测试不得报告为通过。

## 6. 知识与参考

| 涉及内容             | 查阅入口                               |
| -------------------- | -------------------------------------- |
| 模块依赖与架构取舍   | [架构说明](docs/architecture.md)       |
| 任务状态、重试与取消 | [任务状态约定](docs/task-lifecycle.md) |
| 公共 API             | `contracts/openapi.yaml`               |
| 测试环境与用例选择   | [测试说明](docs/testing.md)            |

按任务范围读取相关资料。契约与实现冲突时先定位差异，不自动修改契约来适配当前实现。

## 7. 维护约定

- 命令、契约或任务状态变化时，同步更新对应文档及本文件入口。
- 当前需求、方案和进度放在 `specs/<任务编号>/`，模块细则放在对应模块文档中。
- 清理已确认失效或重复的条目；规范、权限及验收标准的变更遵循 `CONTRIBUTING.md` 中的评审流程。
````

## 步骤 4：写入并检查差异

直接创建或编辑文件，保留已有未提交内容和受管区块。若根文件是指向仓库内正文的软链接，编辑真实正文，保留链接；遇到断链、循环链接或仓库外目标时暂停写入并说明问题。不要顺带修改其他规则文件。

写入前重新读取目标，合并期间新增的修改。写入后读取完整文件并查看差异，检查：

- 路径和命令均有来源，没有虚构内容或占位符。
- 已有业务、授权和验收要求没有被误删或削弱。
- 重复介绍、空章节和任务记录已去除。
- 软链接及共享正文关系保持不变。

按仓库要求运行适用于文档修改的检查。只检查过脚本定义的命令，不得报告为运行通过。已有文件无需改进时，保持不变。

## 步骤 5：交付

给出文件路径，简短列出增加、更新和删除的内容及原因，报告实际执行的检查和未解决的冲突。若修改同步影响共享正文的 `CLAUDE.md`，说明这一点。到此结束，不追加插件推荐或下一轮配置问答。
